# Формат плана

Формат `plan`: план реализации фичи — техническое решение и задачи с файлами `code`.

## Структура

| Что | Заголовок | Свойство | Обязательно | Содержание |
|---|---|---|---|---|
| шапка | `# <ID фичи>: план` | — | да | — |
| Техническое решение | `## Техническое решение` | — | да | ключевые решения реализации и как они связаны, со ссылками на ADR |
| Задачи | `## Задачи` | — | да | только разделы |
| задача | `### [ ] Задача <номер>: <название>` или `### [x] Задача <номер>: <название>` | — | да | список действий — по «Задаче» |
| задача | | `Реализует:` | да | требования и элементы контрактов из `delta/` фичи, включая REMOVED, которые задача воплощает в `code` |
| задача | | `Документация:` | нет | файлы документации из `delta/` фичи, которые описывают сделанное задачей |
| задача | | `Проверка:` | да | чем проверить задачу: тесты сценариев реализованных требований, контрактные тесты элементов |
| Открытые вопросы | `## Открытые вопросы` | — | нет | список вопросов к пользователю |

## Пример

```markdown
# 012-unlock-link: план

## Техническое решение

- ссылка разблокировки — одноразовый токен с ограниченным сроком действия
- токен выдаётся при блокировке аккаунта и хранится в основной базе: adr:unlock-token-storage
- письмо со ссылкой отправляется существующим механизмом писем о блокировке

## Задачи

### [x] Задача 001: Токен разблокировки
Реализует: req:AUTH-007
Документация: doc:auth/login
Проверка: тесты сценариев req:AUTH-007

- Действие: выдача и погашение токена
  - Что:
    - аккаунт получает одноразовый токен на 1 час
    - по токену блокировка снимается, токен гасится
  - Как:
    - отдельный модуль токенов
    - новый токен отменяет прежний
    - погашение и снятие блокировки — в одной транзакции
  - Уровень: архитектурное
    - новая таблица в основной базе: adr:unlock-token-storage
  - Файлы:
    - ADD `src/auth/unlock_token.py`
    - ADD `migrations/0012_unlock_token.sql`

- Действие: токен в письме о блокировке
  - Что: письмо о блокировке содержит ссылку разблокировки
  - Как: блокировка выдаёт токен и передаёт ссылку в существующее письмо
  - Уровень: локальное
    - меняется только блокировка
  - Файлы:
    - MOD `src/auth/lockout.py`

### [ ] Задача 002: Операция разблокировки
Реализует: contract:public-api.unlock
Проверка: контрактные тесты contract:public-api.unlock

- Действие: операция разблокировки
  - Что: клиент разблокирует аккаунт по токену из ссылки — contract:public-api.unlock
  - Как:
    - обработчик гасит токен через модуль токенов
    - ответы и ошибки — по контракту
  - Уровень: локальное
    - новая операция в существующем API
  - Файлы:
    - ADD `src/api/unlock.py`
    - MOD `src/api/routes.py`

## Открытые вопросы

- токен хранить в базе или в кэше?
```

## Задача

Заголовок:
- `[x]` — задача выполнена, `[ ]` — нет
- номер — `001`, `002`, `003`… по порядку
- название — результат задачи, существительным: «Токен разблокировки», а не «Сделать токен»

Действие — пункт `- Действие: <название>`. Вложенные пункты — в этом порядке:
- `Что:` — что получится, языком результата
- `Как:` — как устроено: модули, данные, алгоритм, транзакции. Коротко, без кода
- `Уровень:` — `локальное` или `архитектурное`, причина — подпунктом:
  - локальное — меняется код внутри существующих компонентов
  - архитектурное — меняется устройство системы: новый компонент, хранилище, интеграция или общий формат. Со ссылкой на ADR или блок `architecture`
- `Файлы:` — вложенный список, пункт `` - <пометка> `<путь>` ``. Путь — от корня проекта, пометка:
  - `ADD` — файл создаётся
  - `MOD` — файл меняется
  - `DEL` — файл удаляется

Правила действий:
- действие — законченная часть задачи
- поведение из требований и контракта не пересказывать — ссылка `req:` или `contract:`
- без кода и псевдокода

Объём и порядок:
- каждая часть `delta/` требований и контрактов, кроме шапок, — в `Реализует:` хотя бы одной задачи. Других ссылок в `Реализует:` нет
- каждый файл документации из `delta/` — в `Документации:` хотя бы одной задачи. Других ссылок в `Документации:` нет
- задачи — в порядке выполнения
- задачу можно сделать и проверить отдельно от следующих
- пунктов «Не входит» из Границ `spec` в задачах нет

## Пункты

Общее — по «Оформлению» в `syntax.md`. Для plan:
- в строке пункта с подпунктами — метка и короткое значение, если оно есть: `- Как:`, `- Уровень: локальное`
- между действиями — пустая строка, внутри действия пустых строк нет

## Правка

Правка `plan` после `approved` или изменённой `spec`:
- выполненные задачи не меняются: номер и текст остаются
- расхождение с `spec` — новая задача
- новая задача — в конец, со следующим номером
