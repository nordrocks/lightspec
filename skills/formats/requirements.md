# Формат требований

Формат `requirements`: функциональные требования поддомена — бизнес-правила и наблюдаемое поведение системы для пользователя, включая UI.

## Структура

| Что | Заголовок | Свойство | Обязательно | Содержание |
|---|---|---|---|---|
| шапка | `# <название поддомена>: требования` | — | да | 1–2 строки: какие правила сюда входят |
| шапка | | `Источник:` | да | — |
| требование | `## <ID требования>: <название>` | — | да | только разделы — по «Требованию» |
| требование | | `Источник:` | да | — |
| сценарий | `### Сценарий: <название>` | — | да | шаги `- **<Слово>** <текст>`, затем необязательная таблица значений — по «Сценарию» |
| сценарий | | `Контракты:` | нет | элементы `contracts`, через которые клиент видит сценарий |

## Пример

```markdown
# Вход: требования
Источник: feature:007-login-lockout

Вход по логину и паролю, блокировка после неудачных попыток.

## AUTH-003: Блокировка после неудачных входов
Источник: feature:007-login-lockout

### Сценарий: неудачная попытка входа
Контракты: contract:public-api.login

- **Дано** у аккаунта {было} неудачных попыток входа подряд
- **Когда** пользователь вводит неверный пароль
- **Тогда** система ДОЛЖНА {действие}

| было | действие |
|---|---|
| 3 | увеличить счётчик до 4 |
| 4 | заблокировать аккаунт на 15 минут |

### Сценарий: успешный вход сбрасывает счётчик
Контракты: contract:public-api.login

- **Дано** у аккаунта 4 неудачные попытки входа подряд
- **Когда** пользователь входит с верным паролем
- **Тогда** система ДОЛЖНА обнулить счётчик неудачных попыток

### Сценарий: вход в заблокированный аккаунт
Контракты: contract:public-api.login

- **Дано** аккаунт заблокирован до 14:35
- **Когда** пользователь входит с верным паролем
- **Тогда** система ДОЛЖНА отклонить вход
- **И** сообщить пользователю:
  - причину: «Аккаунт заблокирован»
  - время разблокировки: 14:35

### Сценарий: уведомление партнёров о блокировке
Контракты: contract:events.account-locked

- **Когда** аккаунт блокируется
- **Тогда** система ДОЛЖНА сообщить о блокировке партнёрским сервисам
```

## Требование

- одно бизнес-правило, а не один случай. Изменение одного требования тянет изменение другого — это одно требование
- название — короткое имя правила без технических терминов. Поведение — только в сценариях

## Сценарий

Одна ветка поведения: основной путь, ошибка, граница или исключение. Случаи, которые отличаются только данными, — в таблице значений.

Шаги:
- **Дано** — исходное состояние. Не зависит от состояния — шага нет
- **Когда** — одно действие
- **Тогда** — результат с модальностью: `система ДОЛЖНА`, `НЕ ДОЛЖНА` или `МОЖЕТ`. Минимум один на сценарий
- **И** — продолжает предыдущее слово
- `ИЛИ` запрещено. Два исхода — два сценария

Содержание:
- поведение любого интерфейса, включая UI: экраны, формы, тексты, состояния элементов
- без технических имён: операций, полей, кодов ошибок. Они — только в `Контракты:`
- сценарий с `Контракты:` описывает только то, что клиент видит через эти элементы
- данные, которые получает пользователь, — вложенными пунктами шага, каждый с примером значения
- текст, который возвращает система, — дословно, в «»
- внутренние последствия, например запись в аудит или событие другим сервисам, — отдельным сценарием

Таблица значений:
- `{имя}` в шагах — значение из столбца с этим именем
- таблица — сразу после шагов, одна на сценарий
- строка — один случай с тем же поведением. Новое поведение — новый сценарий
