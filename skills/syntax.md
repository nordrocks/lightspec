# Синтаксис файлов SDD

Синтаксис всех файлов в `specs/`. Формат сущности задаёт только свою схему — по «Схеме сущности».
Скрипты разбирают заголовки, свойства и границы fence. Тело частей для них — текст, в нём ищутся только ссылки.

В файле с ошибкой синтаксиса скрипты не проверяют схему и ссылки. Как они разбирают файл — `engine/README.md`.

## Термины

| Термин | Что это |
|---|---|
| шапка | `#`, его свойства и тело |
| блок | `##`, его свойства, тело и разделы |
| раздел | `###` внутри блока, его свойства и тело |
| часть | шапка или блок |
| тело | строки после свойств и пустой строки, до следующего заголовка |
| имя | у шапки — `#`. У блока и раздела — идентификатор, с которого начинается шаблон заголовка: `<ID требования>`, `<ID элемента>`. Иначе — заголовок целиком |
| узел | то, на что ведёт ссылка: по «Видам ссылок» |

## Пример

````markdown
# <заголовок>
Источник: feature:<ID фичи>
<Имя>: <значение>

<тело шапки>

## <заголовок блока>
Источник: feature:<ID фичи>

<тело блока со ссылкой req:AUTH-007>

### <заголовок раздела>
<Имя>: <значение>

<тело раздела>

```mermaid
<диаграмма>
```
````

- свойства — сразу под заголовком, каждое на своей строке
- тело — после пустой строки
- заголовки — не глубже `###`
- в теле — любой Markdown. Как оформлять — «Оформление»

## Оформление

Для всех файлов, которые пишут скилы. Обязательная структура формата сущности главнее.

| Что описываешь | Форма |
|---|---|
| состояния и переходы | mermaid `stateDiagram-v2` |
| обмен между участниками, порядок вызовов | mermaid `sequenceDiagram` |
| связи частей, ветвление | mermaid `flowchart` |
| однородные данные: параметры, соответствия, сравнение вариантов | таблица |
| последовательность действий | нумерованный список |
| перечисление | список, пункт — одна мысль. Не цепочка через «;» |
| смысл и связь | абзац из 1–3 коротких предложений. Длиннее — нужна таблица, список или диаграмма. Рядом с ними — только то, чего в них нет |

## Идентификаторы

Идентификатор называет форму имени узла или файла. Имена идентификаторов не совпадают с якорями сущностей в `rules.md` и с видами ссылок.

| Идентификатор | Правило | Пример | Что это |
|---|---|---|---|
| `<ID фичи>` | `<номер>-<ключ>` | `012-unlock-link` | фича. `<ключ>` — 2–4 слова |
| `<ID требования>` | `<префикс>-<номер>` | `AUTH-007` | требование. `<префикс>` — всё до последнего `-` |
| `<ID элемента>` | `<интерфейс>.<ключ>` | `public-api.login` | элемент контракта |
| `<ID ADR>` | `<ключ>` | `postgres` | ADR |
| `<ID документа>` | `<домен>/<поддомен>` или `_project/<ключ>` | `auth/login`, `_project/deploy` | файл документации: путь от `main/` без `.md` |
| `<интерфейс>` | `<ключ>` | `public-api` | интерфейс |
| `<домен>` | `<ключ>` | `auth` | домен |
| `<поддомен>` | `<ключ>` | `login` | поддомен |
| `<тема>` | `<ключ>` | `deploy` | тема `project-doc` |
| `<префикс>` | `[A-Z0-9]+(-[A-Z0-9]+)*` | `AUTH` | `<домен>` заглавными буквами |
| `<ключ>` | `[a-z0-9]+(-[a-z0-9]+)*` | `unlock-link` | имя латиницей в kebab-case |
| `<номер>` | `[0-9]{3,}` | `012`, `001` | номер фичи, требования или задачи |

Идентификатор в правиле — другой идентификатор, остальное — регулярное выражение.

### Виды ссылок

Ссылка — `<вид>:<идентификатор>`: `req:AUTH-007`. Вид задаёт идентификатор и узел, на который ведёт ссылка. Где определён узел — «Узлы ссылок» в `rules.md`:

| Идентификатор | Вид | Узел |
|---|---|---|
| `<ID фичи>` | `feature:` | фича |
| `<ID требования>` | `req:` | требование |
| `<ID элемента>` | `contract:` | элемент контракта |
| `<ID ADR>` | `adr:` | ADR |
| `<ID документа>` | `doc:` | документация |

```ebnf
ref         = kind ":" id ;                         (* id — идентификатор вида по таблице *)
kind        = "feature" | "req" | "contract" | "adr" | "doc" ;
```

В заголовках, путях и fence узел пишется без вида: там ссылок нет.

### Поиск ссылок

- свойство с типом `ref` или `list(ref)` — значение целиком: ссылки своих видов, в списке — через `, `. Иное — ошибка
- тело вне fence и свойство с типом `text` — поиском по строке, без разбора:
  - `<вид>:` — начало ссылки, если перед ним начало строки или символ, кроме буквы, цифры, `_`, `-`, `.`, `/`, `:`
  - идентификатор — самый длинный по правилу своего вида. Знак препинания после него — не часть ссылки: `req:AUTH-007.`
  - запись не по правилу — не ссылка: `req:auth-007` скрипты не видят
- заголовки и fence не читаются

## Свойства

Свойство — строка `<Имя>: <значение>` под заголовком. Нет значения — нет строки. Под каким заголовком свойство, обязательно ли оно и что значит — в формате сущности.

### Типы значений

| Тип | Значение | Пример |
|---|---|---|
| `text` | строка текста. Ссылки в ней — с видом, как в теле | `Проверка: тесты сценариев req:AUTH-007` |
| `ref(вид, …)` | одна ссылка — правило `ref` из «Видов ссылок», вид — один из перечисленных | `Источник: feature:007-login-lockout` |
| `list(тип)` | значения типа через `, `, больше ничего | `Реализует: req:AUTH-007, contract:public-api.unlock` |
| `enum(…)` | одно значение из перечня | `Изменение: ADDED` |
| `<тип> \| None` | значение типа или `None` | `Причина: None` |

### Реестр

У имени один тип во всех форматах. «Где» — у каких частей свойство бывает. Обязательно ли оно и что в нём писать — в «Структуре» формата.

| Свойство | Тип | Где |
|---|---|---|
| `Источник:` | `ref(feature)`. В `delta` — `ref(feature) \| None` | шапка и блоки файлов main, у ADR — только шапка. В `delta` — каждая часть |
| `Изменение:` | `enum(ADDED, MODIFIED, REMOVED)` | каждая часть `delta` |
| `Причина:` | `text \| None` | каждая часть `delta` |
| `Статус:` | `enum` — «Статусы спеки» в `rules.md` | шапка `spec` |
| `Основа:` | `list(ref(feature))` | шапка `spec` |
| `Реализует:` | `list(ref(req, contract))` | задача `plan` |
| `Документация:` | `list(ref(doc))` | задача `plan` |
| `Проверка:` | `text` | задача `plan` |
| `Контракты:` | `list(ref(contract))` | сценарий `requirements`, блок `domain-docs` |
| `Тип:` | `enum` — «Элемент» в `formats/contracts.md` | элемент `contracts` |
| `Вход:`, `Выход:`, `Ошибки:` | `list(ref(contract))` | элемент `contracts` с `Тип: операция` |
| `Данные:` | `list(ref(contract))` | элемент `contracts` с `Тип: событие` |
| `Заменяет:` | `list(ref(adr))` | шапка `adr` в `delta` |

## Схема сущности

Формат описывает свой файл таблицей «Структура». Скрипты читают её как грамматику файла.

Строка таблицы — заголовок или свойство:
- строка заголовка: в «Заголовке» — шаблон, в «Свойстве» — `—`
- строка свойства: «Заголовок» пуст. Свойство принадлежит заголовку выше с той же меткой в «Что»

Столбцы:
- **Что** — метка. По ней на строку ссылается текст формата
- **Заголовок** — шаблон. `<…>` из «Идентификаторов» — значение по правилу, другое `<…>` — любой текст. Варианты — через «или»
- **Свойство** — имя свойства
- **Обязательно** — `да`, `нет` или `если <условие>`. Условие проверяет агент, скрипты считают `нет`
- **Содержание** — что писать. «только разделы» — тела нет, сразу `###`

Правила:
- заголовки и свойства — в порядке строк таблицы
- `###` — раздел ближайшего `##` выше
- заголовок с `<…>` повторяется подряд сколько угодно, без `<…>` — не больше раза
- идентификатор в заголовке совпадает с путём файла: `<ID фичи>` — с папкой фичи, `<интерфейс>` — с именем файла, `<префикс>` — с `<домен>`
- имя уникально: ID требования — в домене, имя блока — в файле, имя раздела — в блоке
- свойства и разделы зависят от значения свойства — отдельная таблица `` | `<Имя>:` | Свойства | Разделы | ``, как «Элемент» в `formats/contracts.md`. Свойства и разделы, которых в ней нет, — у всех
